### Validate before deletion

Current `deleteByToken` splits the credential and deletes by selector without comparing the validator hash. Reuse the full-token validation already implemented by `findByToken`:

```java
public void deleteByToken(String rawToken) {
    if (rawToken == null || rawToken.isBlank()) {
        return; // HTTP request validation still rejects blank logout requests.
    }
    RefreshToken stored = findByToken(rawToken);
    if (refreshTokenRepository.deleteBySelector(stored.getSelector()) != 1) {
        throw new InvalidRefreshTokenException(
            "Refresh token has already been consumed");
    }
}
```

Return the affected row count from the repository:

```java
public int deleteBySelector(String selector) {
    RefreshTokenDbExample example = new RefreshTokenDbExample();
    example.createCriteria().andSelectorEqualTo(selector);
    return mapper.deleteByExample(example);
}
```

This requires updating mock-based service tests: a successful deletion must stub a return value of `1`. Verify that a wrong validator does not call the delete method, and that a zero-row deletion is rejected.

### Consume once and replace in one transaction

A focused initial fix can put a transaction around the existing refresh controller method; a later cleanup can move the orchestration into a separate service. Do not introduce self-invocation that bypasses Spring's transactional proxy.

```java
@PostMapping("/refresh")
@Transactional
public ResponseEntity<RefreshResponse> refresh(
        @Valid @RequestBody RefreshRequest request) {
    RefreshToken stored = refreshTokenService.findByToken(request.getRefreshToken());
    if (refreshTokenService.isTokenExpired(stored)) {
        refreshTokenService.deleteByToken(request.getRefreshToken());
        // A normal return commits removal of the expired token.
        return ResponseEntity.status(HttpStatus.UNAUTHORIZED).build();
    }

    User user = userService.getUserById(stored.getUserId());
    refreshTokenService.deleteByToken(request.getRefreshToken());
    String replacement = refreshTokenService.createRefreshToken(user.getId());
    String access = jwtService.generateToken(user);

    return ResponseEntity.ok(RefreshResponse.builder()
        .token(access)
        .expiresIn(jwtService.getExpirationMs())
        .refreshToken(replacement)
        .build());
}
```

The deletion count ensures only one concurrent transaction consumes the old row. The transaction rolls deletion back if replacement creation fails. An expired-token branch that throws after deletion would roll back that cleanup unless transaction semantics are deliberately changed.

### Required verification beyond mocks

- Two concurrent refresh requests with one real token against PostgreSQL: exactly one success, one 401, one replacement token.
- Replacement insertion fails: old token remains usable after rollback.
- After successful refresh: old token returns 401; replacement succeeds.
- Logout using a known selector and an incorrect validator returns 401 and does not revoke the valid token.
- Repeated logout with an already-revoked token returns the chosen documented status (401 for this proposal). Frontend logout must tolerate it.

Concurrent browser tabs require a separate policy. Sharing one observable coordinates requests within one tab, not across tabs. Test two tabs; if both rotate the shared credential, consider cross-tab coordination before claiming seamless multi-tab session recovery. Do not weaken server-side single-use guarantees to hide the race.

## 6. B4: repair Angular refresh coordination and logout

### Why the existing flow is unreliable

1. `toObservable` needs an injection context (or an explicit injector). The asynchronous error callback is not guaranteed to have one.
2. Waiting requests filter for a successful token, but `failRefresh()` never signals a terminal error to them.
3. Login and logout 401s enter the generic refresh path. A rejected logout can cause refresh followed by another logout.
4. The catch around both refresh and retry treats a failed application retry as an authentication failure.
5. A delayed 401 from an old access token can trigger an unnecessary second rotation.

[Angular injection-context documentation](https://angular.dev/api/core/rxjs-interop/toObservable) and [HTTP testing documentation](https://angular.dev/guide/http/testing).

### Proposed shared refresh operation

Replace the refresh-lock signals and their `startRefresh`, `completeRefresh`, and `failRefresh` methods. Keep token storage unchanged in this branch; moving credentials out of localStorage is a separate authentication design change.

```typescript
// AuthService imports, in addition to existing Angular imports:
import {
  Observable, Subject, catchError, finalize, of,
  shareReplay, takeUntil, tap, throwError
} from 'rxjs';

private refreshRequest$: Observable<RefreshResponse> | null = null;
private readonly sessionEnded$ = new Subject<void>();

refresh(): Observable<RefreshResponse> {
  if (this.refreshRequest$) return this.refreshRequest$;
  const refreshToken = this.getRefreshToken();
  if (!refreshToken) {
    return throwError(() => new Error('No refresh token available'));
  }

  this.refreshRequest$ = this.http.post<RefreshResponse>(
    `${this.API_URL}/refresh`, { refreshToken }
  ).pipe(
    takeUntil(this.sessionEnded$),
    tap(response => {
      this.setToken(response.token);
      this.setRefreshToken(response.refreshToken);
    }),
    catchError(error => {
      this.logout();
      return throwError(() => error);
    }),
    finalize(() => { this.refreshRequest$ = null; }),
    shareReplay({ bufferSize: 1, refCount: false })
  );
  return this.refreshRequest$;
}

logout(): void {
  const refreshToken = this.getRefreshToken();
  this.sessionEnded$.next(); // Cancel an in-flight refresh before clearing state.
  this.clearToken();
  this.clearRefreshToken();
  this._currentUser.set(null);
  void this.router.navigate(['/login']);

  if (refreshToken) {
    this.http.post(`${this.API_URL}/logout`, { refreshToken }).pipe(
      catchError(() => of(null))
    ).subscribe();
  }
}
```

Cancel prior refresh work on a successful new login before storing that new session's credentials too. Otherwise an old refresh response can overwrite the new login. On an invalid session discovered by `loadCurrentUser`, clear both credentials, not just the access token.

Treat cancellation as a separate case from refresh rejection. A cancelled observable can complete without a value. `app.config.ts` uses `firstValueFrom`; ensure startup ends with a value or handles empty completion, for example by applying `defaultIfEmpty(null)` to the user-loading stream. Avoid turning transient network errors into an undocumented permanent logout policy; decide and test the intended behavior.

### Proposed interceptor

```typescript
import { HttpErrorResponse, HttpInterceptorFn } from '@angular/common/http';
import { inject } from '@angular/core';
import { catchError, switchMap, throwError } from 'rxjs';
import { AuthService } from '../services/auth.service';

export const AuthInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthService);
  const publicAuth = /\/auth\/(login|register|refresh|logout|verify-email|resend-verification|forgot-password|reset-password)(?:[/?#]|$)/.test(req.url);
  if (publicAuth) return next(req);

  const sentToken = auth.getToken();
  const outgoing = sentToken
    ? req.clone({ setHeaders: { Authorization: `Bearer ${sentToken}` } })
    : req;

  return next(outgoing).pipe(
    catchError((error: HttpErrorResponse) => {
      if (error.status !== 401 || !auth.getRefreshToken()) {
        return throwError(() => error);
      }
      const currentToken = auth.getToken();
      if (currentToken && currentToken !== sentToken) {
        return next(req.clone({
          setHeaders: { Authorization: `Bearer ${currentToken}` }
        }));
      }
      return auth.refresh().pipe(
        switchMap(response => next(req.clone({
          setHeaders: { Authorization: `Bearer ${response.token}` }
        })))
      );
    })
  );
};
```

This assumes all intercepted business calls are to TaskFlow, as in the current app. Before introducing third-party HTTP calls, scope both URL-prefixing and bearer attachment to the API origin/path so credentials never leave TaskFlow.

## 10. V1: inspect selector migration before any schema changes

`20260513.1-AddSelectorToRefreshTokenTable.sql` adds a non-null selector with default `''`, then creates a unique constraint. If the table contains multiple old rows, they all receive the same selector and the constraint cannot be created. This is a conditional upgrade defect, not proof that the current QA database is broken.

Read-only checks for the deployment owner:

```sql
SELECT id, filename, dateexecuted
FROM databasechangelog
WHERE id LIKE '%RefreshToken%'
ORDER BY dateexecuted;

SELECT COUNT(*) AS refresh_token_count FROM refresh_tokens;
```

If the selector migration has applied, do not edit its released contents and trigger checksum mismatches. If QA has not applied it and legacy rows exist, plan an explicit pre-upgrade invalidation of old refresh sessions or a compatible backfill before adding uniqueness. Record the user impact (sign-in again), back up first, and make the migration valid for both empty and populated databases. A later changeset cannot fix a migration that fails before reaching it.
